# Hermes memory source audit

Checked on 2026-10-29 against the official `NousResearch/hermes-agent` repository. This is a source audit, not a claim that Hermes' hosted service or every model/provider was exercised.

## What is actually on by default

| Capability | Verified default and conditions |
| --- | --- |
| Built-in curated memory | `memory_enabled=true`, `user_profile_enabled=true`. `MEMORY.md` has a 2,200-character budget and `USER.md` a 1,375-character budget. These are curated notes, not the full conversation archive. |
| Memory review cadence | `nudge_interval=10`, measured in user prompts. It advances only when the memory tool and store are available. Setting the interval to zero disables the trigger. |
| Skill review cadence | The installed example configuration has `creation_nudge_interval: 15`, measured in **tool-calling iterations**, not user turns or individual tool calls. The runtime fallback for an absent key is **10** tool iterations. New configuration seeding normally copies the example; the fallback value must not be confused with the seeded value. |
| Automatic background review | `auxiliary.background_review.enabled` defaults to true, but it is conditional, not an unconditional process after every turn. The trigger must fire, the turn must have a response and not be interrupted, review must not be skipped, and an automatic delegate review must not recurse. Safe-worker and finite gateway turn modes suppress automatic review. |
| General write approval | `memory.write_approval` and the shared subsystem gate default to false. Enabling the gate stages background writes and skills writes; foreground memory may use an interactive approval callback or stage if none exists. |
| Unattended destructive memory writes | Independently of the optional general approval setting, background-review `patch` and `remove`, including batch operations, are staged for owner approval. `add` remains available. Failure to stage is a refusal. Explicit attended refinement has a separate path. |
| External memory provider | Not selected by default (`provider` is empty); it is not required for built-in memory or historical session search. |

Hermes' cron constructor uses `skip_memory=False` and `skip_background_review=True`: cron can retain memory access while automatic review forks are suppressed. Mau reads a fresh screened memory view for each scheduled Agent execution, fixes it for that request's retries, and denies scheduled memory tools and writes. This read-only boundary is an explicit product policy, not a literal copy of Hermes' cron behavior. ## Why a copied conversation alone is insufficient

Hermes structurally clones the transcript. On its same-model path, it can preserve the parent's advertised tool schema and cached prompt, while enforcing a **separate dispatch allowlist**. That allowlist permits memory only when the memory trigger fired and memory is enabled; it permits skill-management tools and read-only file inspection. Arbitrary file-write, terminal, message and unrelated tools are denied unless a trusted profile explicitly adds named extra tools. The review agent disables recursive nudges, session persistence, external memory-provider attachment and status output; it has a noninteractive dangerous-command denial callback. A differently routed model receives a digest instead of the same-model full snapshot. [Fork construction and isolation](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/agent/background_review.py#L958-L1059), [allowlist and execution](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/agent/background_review.py#L1092-L1223).

Mau's ordinary native fork preserves the Codex tool binding, and its ordinary per-turn settings do not constitute an all-native-tool denial policy. `MemoryReviewCoordinator` therefore records `unsupported` without fetching history or starting a model when no trusted `RestrictedMemoryReviewer` is provided. That port must attest and implement a separately restricted runtime, scoped memory/skill effects, staged destructive writes, disabled delivery and recursion, and denial of every other native or dynamic tool. A prompt or business-tool grant is not evidence of this isolation.

The implemented coordinator counts completed owner turns, records due work before asynchronous I/O, checks the source's owner run, copies full native history through Router's public `WorkSessions`, and submits into a separate review session. This is a capture at review preparation time, not a claim to have retained an exact turn-end native snapshot. A changing or active source defers preparation. Exceeding the configured history or byte bound refuses the copy rather than silently presenting partial history as complete. A lost submission response is reconciled by stable event ID; it is not replayed. Review output is not delivered to the owner conversation. The persisted foreground reminder is separate from the ability to execute a background review.

Mau defaults follow the seeded 10-user-turn / 15-tool-iteration cadence. A missing trusted tool-iteration measurement does not count toward skill review; a dynamic callback count cannot substitute for it. Mau does not claim that the default Codex employee profile already satisfies the restricted reviewer contract. The separately provided [restricted Codex review adapter](restricted-memory-reviewer.md) implements submission against an explicitly provisioned, version/model-pinned runtime; its native dispatch checks used a deterministic local provider, not a production model. It reports skills unavailable unless a real scoped native-managed skill dispatcher is bound.

## Historical search is separate from curated memory

Hermes' `session_search` reads the SQLite session archive; it does not call an LLM or automatically summarize all history. Its four shapes are discovery, read, scroll and browse. Discovery uses FTS5, deduplicates lineage, and adapts result detail. It hides worker/subagent/tool sources from discovery, demotes cron matches rather than excluding all cron content, and excludes current live context while allowing appropriate compacted/archive content. Explicit profile selection can open another profile's database read-only; a bare session ID does not scan every profile. A multi-owner service must enforce its own authenticated owner/employee scope rather than copying local profile access as a permission model. [Session search implementation](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/tools/session_search_tool.py).

## Scanning is an advisory defense

Memory mutations scan candidate content. Loading memory scans the prompt snapshot and replaces matched entries with blocked placeholders while retaining their original stored text for inspection/removal. The scanner is a finite regular-expression library with NFKC normalization and selected invisible-codepoint detection; it caps input at 65,536 characters and explicitly describes itself as advisory. It does not normalize all cross-script confusables or prove that arbitrary language is safe. Neither a passed scan nor memory content grants authorization. [Memory store and frozen snapshots](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/tools/memory_tool_store.py#L223-L255), [threat-pattern scope and bound](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/tools/threat_patterns.py#L1-L17), [scan implementation](https://github.com/NousResearch/hermes-agent/blob/ef75bc708867e3884cb40a91363be6dc6fddc034/tools/threat_patterns.py#L131-L159).

Mau-specific choices such as duplicate rejection, the exposed replace operation, owner/employee authorization, scheduled-write restrictions, or conservative failure handling must be documented as such rather than attributed to Hermes verbatim.
