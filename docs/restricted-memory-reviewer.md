# Restricted background review adapter

`CodexRestrictedMemoryReviewer` implements actual review submission, lookup and cancellation using Router's public `WorkSessions`. `MemoryReviewCoordinator` performs cadence, context capture, deduplication and recovery. The default Mau configuration has no restricted runtime binding and reports `unsupported`; providing a prompt or enabling a boolean does not start a background model.

The baseline in `codexReviewProfile()` is pinned to Codex **0.165.0**, source commit `360319d8dee62d87e2d59fc0c21805d79519cfed`, model **gpt-5.4**, a dedicated Responses provider, and the bundled model catalog. It adapts Codex's official [temporary structured request](https://github.com/openai/codex/blob/360319d8dee62d87e2d59fc0c21805d79519cfed/codex-rs/tui/src/temporary_structured_request.rs#L46-L158) configuration. It selects no execution environments, workspace roots or capability roots; disables kernel tool features and inherited context-file loading; and retains only trusted, server-dispatched memory tools. A read-only sandbox by itself is insufficient.

The adapter rejects different native versions, model or thread settings, custom `model_catalog_json` / provider `model_catalog_url`, enabled MCP servers, OAuth model-discovery paths, and API-key model discovery. The old `remote_models` feature is removed in this Codex version and is not used as a safety guarantee. Changing this baseline requires new native validation, not merely updating a version string.

## Provisioning and connection

1. Use [the Host CLI profile](../examples/restricted-review-host.json) and [dedicated provider configuration](../examples/restricted-review-provider.toml) as templates. The generated JSON uses the public Host `command`, `args` and `env` fields. It intentionally exposes no caller `allowedSettings`; the model is frozen in `thread.model`. Create private review HOME, CODEX_HOME, workspace and Host-state directories. Do not reuse an employee's HOME, workspace, MCP configuration or model catalog. No example contains an account or credential.
2. Provision a separate Router review worker/runtime through the existing embedding APIs. Its owner must match the source employee. A separate worker may have a different agent ID, but its trusted memory dispatcher must bind to the **original employee's** memory. The adapter refuses a binding that points to the worker's own memory instead.
3. Install a server-side dispatch allowlist. Only managed memory operations and explicitly provided native-managed skill operations may execute; all other product and channel tools are denied. Label memory writes as review-origin in every state, including submission, cancellation and uncertain outcomes; destructive operations must stage for owner approval. Do not derive this label from model text or only from a `running` status. A submitted source transcript is untrusted evidence, never authorization.
4. Implement the trusted `resolve(scope, signal)` dependency from the launcher's actual installed configuration and live dispatcher. Return `ReviewRuntimeBinding`: authenticated original employee scope, the review `WorkSessions`, the installed profile, its `reviewProfileDigest()`, dedicated-home and bundled-catalog evidence, and the dispatch policy. The resolver is an in-process trusted service boundary; it is not an HTTP endpoint accepting an attestation supplied by a user or model. It must invalidate its evidence when the launched configuration, catalog or dispatcher changes.
5. Construct `new CodexRestrictedMemoryReviewer({ resolve })` and supply it as `createMau`'s trusted `reviewer` dependency. The adapter itself checks the native version through `discover()` and the effective provider/MCP configuration through the read-only `config/read` native method. Each submission is checked again. It calls `WorkSessions.submit` with stable event/session IDs, delegation provenance, empty connector/business grants, a tool-call limit and an expiry. It never forks, delivers, or sends a follow-up message.

This adapter does not provision the worker or assert that an arbitrary existing runtime is restricted. The launcher's installed-profile and dispatcher evidence remains a required integration responsibility. `lookup` and `cancel` remain available after policy revocation so that an uncertain or running review can be reconciled safely.

## Skills boundary

The default binding must use `skills: { mode: "unavailable" }`; capabilities then report `skills: false`. Codex's `skills/config/write` enables or disables a discovered skill; it is not a general skill-content authoring API. This change adds no parallel skill filesystem manager. A trusted integration may advertise `native-managed` skills only when an actual scoped skill dispatcher exists, with exactly its tool names in the dispatch allowlist. Merely naming a tool `skill_manage` is not evidence that such a dispatcher exists.

## Verification performed

- 13 coordinator tests cover cadence, non-owner exclusion, runtime capability refusal, scope, history copying, lost-response recovery, cross-session non-reentrancy, cancellation, restart and a competing coordinator.
- 8 adapter tests cover public profile shape, mutable-policy rejection, native-version and effective-config checks, original-employee versus worker identity, submission provenance and budgets, skills unavailable by default, policy revocation, snapshot binding and cancellation.
- An isolated actual Codex 0.165.0 executable was run with the **exact exported profile**, an empty temporary HOME/CODEX_HOME, and a deterministic loopback Responses provider. The profile parsed with Host's public `configSchema`; the adapter accepted the actual native version and effective config. The model tool list contained only `memory_probe`, and that dynamic tool completed successfully. Forced calls to `exec_command`, `apply_patch`, `collaboration.spawn_agent`, code-mode `exec`, `list_mcp_resources`, `view_image` and `send_message_to_user_async` each returned an unsupported-call result. A further check loaded the generated JSON using public `createConfiguredRuntimes`, started the Host HTTP server, and completed a managed run with the same single-tool surface. Ten scenarios used 18 local provider requests.

These are protocol/dispatch checks with a local provider, not an external-model quality evaluation, OAuth acceptance test, cloud deployment or proof against a trusted operator changing the runtime. No production employee, account or session was touched. The locally generated probe and report are under `.local/memory-review-audit/`; the exact baseline and portable fixtures are in the source and tests named above.
