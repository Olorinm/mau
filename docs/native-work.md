# Native work integration

Mau composes Router's public `WorkSessions` API and Host's native adapters. Codex remains responsible for its threads, turns, compaction, skills, memory pipeline and tool/approval semantics. Public Router work session IDs are routing IDs, not native Codex thread IDs.

## Configuration

The Mau setting `"nativeWork": {"partnerTools": true}` enables stable product tools for admitted owner turns and partner turns: `partners`, `memory`, `session_search`, and `proactive_work`. This setting defaults to false to avoid silently changing the tool definition fingerprint of existing native sessions. It does not create rules or authorize accounts. Changing a connector account does not change the stable tool definitions.

A session keeps the tools and the instructions it began with: Mau stores both per Host session and sends them unchanged with every later turn, so a change to the tool definitions never invalidates an existing session. Such a session does not see tools that were added later. It gets them when its conversation starts a new window ("new chat", `/new`), which opens a new Host session. A tool that was removed since (`work_sessions`, `employee_memory`, `business_data`) is still listed in a session that began with it; a call to it is answered at once with `tool_removed` and the advice to start a new conversation.

Use [host-native-work.json](../examples/cloud/host-native-work.json) as the trusted Host profile for skills/memory management. The runtime `nativeAccess` allowlist is server-owned and defaults closed when omitted. A method being allowed does not mean the installed Codex supports it: memory endpoints are experimental and native errors are retained. This profile does not enable native memory generation. Enable it only after selecting and verifying the runtime's own native home and memory trust boundary. Private owner work and public group work must not share private memory merely because they use different thread IDs.

Host preserves server notifications in its native event stream. `nativeAccess.notifications` permits outbound client notifications; it is not an event subscription and is deliberately absent from this profile.

Skill files can be delivered through the existing environment profile `files` list and persisted with the partner's files. Codex discovers and loads them. The skills management API enables/disables only paths returned by a fresh native `skills/list`; arbitrary local file paths cannot become configuration writes. File updates and root selection remain trusted environment setup.

## Public product operations

All routes below are under `/_mau/v1`, require the signed-in owner, and recheck partner ownership. Native reads do not automatically wake sleeping environments; an explicit environment resume is separate. Router's session/event management routes remain available under its public communication API.

| Route | Behavior |
| --- | --- |
| `POST /agents/:id/native/discover` | Read current Host/runtime discovery. |
| `GET /agents/:id/native/skills` | List actual native skills. |
| `POST /agents/:id/native/skills` | `{path, enabled}` for an already discovered skill. |
| `GET /agents/:id/native/memory` | Native memory status, if the runtime exposes it. |
| `GET /agents/:id/model-settings` | The models and efforts the kernel reports and the runtime's `allowedSettings` permit, with the owner's choice. Read from the running kernel; while the environment is not running, the last reading is returned (`source: "saved"`). |
| `PUT /agents/:id/model-settings` | `{model?, effort?}`, each a listed value or `null` for the runtime's default. Router sends the choice with every following turn of the partner. |
| `GET /agents/:id/work-sessions/:sessionId/memory` | Read native thread memory through its authenticated Host binding. |
| `POST /agents/:id/work-sessions/:sessionId/memory` | `{mode: "enabled" | "disabled"}` through the authenticated Host binding. |
| `GET/POST /agents/:id/memory` | Read the memory document / execute a bounded memory operation. |
| `POST /agents/:id/memory/search` | SQLite original-history search with explicit index coverage. |
| `POST /agents/:id/memory/history/import` | Import one page from this partner’s native history, using `{sessionId,cursor?}`. |
| `GET /partners` | The owner's partners: `id`, `name`, `duty`, `kernel` (the kernel that partner runs on), `model`, `effort`, `status`, `lastActivityAt`, `waiting: { messages, approvals }`, and where they apply `sharesEnvironmentOf`, `recruitedBy: { id, name }`, `recruitedAt`, `dismissedAt`. |
| `GET /agents/:id/sessions` | The sessions the partner works in beside its conversation with the owner. `data`: the 60 that began last, oldest first, or with `?before=<id>` the ones that began before that session (`limit`, at most 200); `earlier` is the id to ask before for the page before this one, or `null`. `active`, without `before`: up to 60 sessions a turn runs in or something happened in last, however long ago they began. Each has `id`, `chatId` (the chat its events are read from), `title`, `startedBy`, `createdAt`, `lastAt`, `turns`, `turns` (the turns that ended in it, in every context it had), `tokens` (the size of its context after its last turn, when the kernel reports one) and `working`. |
| `POST /agents/:id/sessions/:sessionId/messages` | `{ text, key }`: the owner writes in one of those sessions. It is a turn of that session with the owner's own authority, and its answer stays in the session; the partner that opened the session is not told. The same `key` is the same turn. `404 partner_session_not_found`. |
| `GET /partners/messages` | Messages between the owner's partners, newest first (`?agentId=` for one partner, `?limit=`, 50 by default and at most 200): `from`, `to`, `intent`, `text`, `status`, `connectionId`, and when known `sentTo` (the kernel, model and effort the turn was submitted with), `result`, `deliveredBy`, `reason`. Messages that ended more than 30 days ago are no longer listed. |
| `POST /agents/:id/dismiss`, `/restore` | `{}`. Archive a partner, or bring it back. `GET /agents` and `/agents/:id` return `dismissed` (a time, or `null`). |
| `GET/POST /proactive` | List/create owner rules. |
| `GET/PUT /proactive/:id` | Read or replace with `{expectedVersion, rule}`. |
| `GET /proactive/:id/runs` | Cached run records and distinct notification receipts, without waking the Host. |
| `POST /proactive/:id/state` | `{status: "active" | "paused"}`. |
| `POST /proactive/:id/run` | `{requestId}` for a stable manual trigger. |
| `POST /proactive/:id/cancel` | Cancel the known active event; pausing alone does not cancel. |

`memory` maintains the partner's one bounded MEMORY.md; it does not edit Codex-generated native memory. Scheduled Agent work receives a fresh screened read-only view per event, saved for identical retries, and cannot invoke memory tools. See [Hermes memory](hermes-memory.md) for snapshots, approval, history and background-review boundaries.

The `proactive_work` tool supports rule creation/update and inspection/pause/resume/manual run. Changes require an owner-admitted turn; a partner turn may only inspect rules and run history, so that a message between partners cannot create persistent background permission. Pausing takes effect at once. Creating a rule, changing what a rule does and enabling one wait for the owner: nothing is saved, the tool answers `awaiting_owner_confirmation`, and the owner gets a card in their conversation with the Agent (Router's owner request, which belongs to no run and only the owner answers) showing the schedule, the whole instruction, the connections it may read and where results go. Confirmed, the rule is saved enabled; a rule that exists keeps its saved version and state until then. Rejected, or unanswered for three days, nothing changes. A newer proposal for the same rule, the owner's own save or a state change withdraws the card, and at most five cards of one Agent wait at a time. Rules saved through the owner API above take effect directly.

## Partners

A partner is an Agent of the owner: its own Router identity, its own conversation with the owner, its own memory and model settings, and one line saying what it is responsible for (its duty). The `partners` tool lets a partner work with the owner's other partners. It is not a sub-agent mechanism: a kernel's own sub-agents stay helpers inside one turn and are not managed here.

| Action | Behavior |
| --- | --- |
| `roster` | The owner's other partners (name, duty, kernel, model, effort, status, last activity, what waits at each), the caller's messages that wait for replies, and the limits. With `guide: true` also what a recruit may choose (`kernels`: the kernels of the caller's environment, its own first; `models` with their efforts, `efforts` and `yours` for the caller's own kernel; and, where the environment offers other kernels, `otherKernels` with each one's `models`, `efforts` and `default`, and a note) and the guide. Reading what another kernel offers starts that kernel, so it happens only then. `includeDismissed` also lists dismissed partners. In an environment with one kernel the roster has no member about other kernels. |
| `recruit` | `name` and `duty`, optionally `kernel`, `model`, `effort`, and a first `message` with `intent`. The new partner runs in the recruiter's environment (the one the recruiter shares, when it shares one) and needs no approval. `kernel` accepts any kernel the roster lists: the partner is bound to that kernel's runtime of the same Host, in the same working directory, and keeps it. Left out, it is the recruiter's kernel, and `model` and `effort` left out are the recruiter's own; on another kernel nothing is carried over, and what is left out is that kernel's default. Only values the roster lists for the kernel are accepted; anything else is refused with the allowed values (`partner_kernel_not_available`, `partner_model_not_available`, `partner_effort_not_available`), never replaced by a default. A listed kernel whose runtime the environment's Host does not have available is refused with `partner_kernel_not_available` and `reason: kernel_runtime_unavailable` before anything is created. A name that exists is refused (`partner_name_taken`), unless that partner was dismissed: then it is restored, on the kernel it has (`kernelKept` when the recruit named another). |
| `message` | `to`, `text`, `intent`, and optionally `session` or `title`. `relay` passes on what the owner asked for, `ask` is the sender's own question; both expect a reply and run in a session of the recipient: a new one, titled with `title` or the first line of the message, or the one `session` names, when the sender opened it (`partner_session_not_found`). The answer of the call carries `session` and `title`. `inform` expects none and starts no turn anywhere: the recipient reads it at the start of its next turn. A partner whose environment a message cannot wake (paused, being deleted, in need of attention, or missing) is refused at once with `partner_unavailable`. |
| `wait` | Waits up to 60 seconds (default 30) for replies, to the caller's waiting messages or to `messageIds`. A reply the turn that sent the message reads this way is not delivered a second time, once the answer of the `wait` call has reached that turn; if it did not (the call timed out at the Host), the reply comes back as a turn. A result stays readable by its id afterwards, and reading the result of an earlier turn's message does not stop its delivery. While a `wait` runs, a stop request for that turn takes effect when the `wait` returns. |
| `sessions` | Without `name`, the caller's own sessions by context, the one used last first, 20 a call (`offset`; `nextOffset` when there are further ones): its conversation with the owner, and one for each piece of work a partner sent it. Each has `id`, `title`, `startedBy`, `first` (how its first request begins), `turns`, `tokens` when known, `from`, `to` and `state` (`working`, `idle`, or `closed` with `continuedIn` for a context its session has left); a context that continues an earlier one names it as `continues`. With `name`, the sessions the caller opened at that partner, the one that began last first, 20 a call with the same `offset`: `id`, `title`, `turns`, `tokens` when known, `lastAt` and `state` (`working` or `idle`). A partner never sees the sessions another partner opened. It works in every turn, also one that handles a partner's message. |
| `dismiss` | Archives a partner: its Agent, conversation and memory are kept, it leaves the roster, and it is not messaged. Recruiting its name restores it. Only a turn the owner started may dismiss. |

**Where a message runs.** A `relay` or `ask` is a turn of a session of the recipient, submitted with the sender as its `sender`: a context of its own, which begins with the recipient's instructions, tools and memory and nothing of its earlier work. One piece of work is one session; the sender continues it by naming it, and sends anything else without. Sessions of one partner run side by side, in the same environment and on the same files. The owner finds the message, marked as sent by the other partner, and the answer in that session, which the console shows as a thread of the recipient's page. An agent on the owner's own computer has no sessions of this kind: a message to it is a turn of its conversation with the owner, as before. The recipient reads one JSON object: `from.partner` (the sender's name), `sent` and `message`. It cannot ask the owner in that turn: its questions are not presented. What such a turn is (its answer goes back to the sender; answer with what is missing so that the sender asks the owner) is said once, in the `partners` tool's description.

**How the reply returns.** When the recipient's turn ends, Mau submits a turn to the conversation the message was sent from, with Router's `reply` on the connection the owner used there, so the sender's answer reaches the owner on the web or the channel the owner wrote on. The turn's input is one JSON object with `results`: for each result the partner (`to`), the original message, the status, the duration, and the answer. The kernel, model and effort the partner's turn was submitted with stay on the message record (`sentTo` in the owner's API), not in what the model reads. `action=wait` returns the same members. That a partner's answer is its own report, and that a result that is not completed is final, is said in the `partners` tool's description.

**Sessions that began with another description.** A session keeps the tool definitions it began with. When the `partners` tool's description or input differs from the one a partner's sessions began with, Mau continues that partner's conversation with the owner in a new window, once, as the owner's own "new conversation" does: the next turn opens a session with the current tools, and the transcript, memory and files stay. Nothing is cancelled for it; a conversation in which a turn runs or an input waits is moved when it is idle, and so is one that a reply is still on its way to, because a result that arrived in the new session would be read by a model that never sent the message. The owner sees the divider of a new conversation in that partner's chat.

**Sessions that grow large and cold.** Mau counts what each session was used for: its turns, and the size of its context after each run as the kernel reported it (Codex, Claude, ACP and Pi kernels do; Hermes and OpenClaw report none in their events, and a session whose kernel reports none is never judged by its size). A context that holds more than 250,000 tokens and has not been used for a day is not continued, because going on in it would read all of it again at full price. Its session goes on in a new context, as a conversation does after the owner's own "new conversation": one transcript with a divider, the same session id for its sender and the same thread for the owner. A turn in the new context is told one line, where the earlier part is (`continues`), until one has completed; what it reads of it, with `session_search`, is its own choice. It does not happen while a turn runs or waits in the session, whoever wrote it, nor, for a conversation, while a reply is on its way to it. The size is that of the session's own thread: what a kernel's sub-agents report in the same run is left out (a thread Codex spawned, a Claude message with `parent_tool_use_id`, an OpenCode child session). A size is recorded only when it is known to be the session's own and its last: a Codex run whose events no longer say which thread the session is bound to, and a run whose events were not read to the end, record none. A context whose last run recorded none has no size until a run records one: the size of the run before is not used. Results that are ready together reach their sender in one turn (at most eight). A result is handed over only when the turn that sent its message has ended and that turn's answer is recorded in the conversation, so the result stands after it.

**Authorization.** A message is not the owner's authorization. The recipient's turn is admitted as a delegation whose grants are what the sending turn could use within the connections assigned to the recipient; whether connected-app writes can ask the owner follows the sending turn. The turn that hands results over acts within what the turns that sent those messages could use. Connections that act as the owner's personal identity are outside all of this: they work only in a turn the owner started in the owner's private conversation with a partner, and are refused in a turn that handles a partner's message and in a turn that hands a result over (`connected_app_owner_private_only`). When one is needed, the owner asks that partner directly in its own conversation. See [connector approvals](connector-accounts.md#approvals-for-a-partners-turn).

**Limits.**

- One layer: a turn that handles a partner's message can read the roster, and cannot recruit, message or dismiss (`partner_layer_limit`).
- A sender may have four messages waiting for replies. A further one is refused, not queued (`partner_message_limit_reached`). An `inform` is not counted; twenty of them may wait for one partner's next turn (`partner_note_limit_reached`).
- A turn that hands results over may send messages again. Four such generations may follow one message of the owner; the next is refused until the owner writes (`partner_chain_limit`).
- Partners are recruited, messaged and dismissed only from the owner's private conversation with the caller, because that is where a reply returns. Other owner turns (a group of the owner and the owner's Agents, work submitted through Router's work-events API) can read the roster; the rest is refused with `partner_owner_conversation_required`.
- A message is at most 16,000 bytes. An answer longer than the room one Router input has is cut in the hand-over and says so; the full answer is in the recipient's conversation.

**What a console is given.** The input of a partner turn is text written for a model. Mau submits it with Router's `display`, which the web chat API returns on the event and which is no part of the model's input: `partnerMessage` (`id`, `intent`, `from: { id, name }`, and `text` as the sender wrote it) on a message in the recipient's conversation, and `partnerResults` (for each result `messageId`, `partner: { id, name }`, `intent`, `status`, `error`, `answer`, `cut`, `durationMs`) on the turn that hands results over. The answers there share 48,000 bytes; `cut` says how many characters a long one lost, and the whole answer is in that partner's conversation. An approval card of a partner carries `card.display.partnerApproval` (see [connector approvals](connector-accounts.md#approvals-for-a-partners-turn)).

**Delivery.** The record of every message is kept in Mau's store (`partner_messages`) for 30 days after it has ended, with what became of it:

| Status | Meaning |
| --- | --- |
| `queued` | An `inform` that its recipient's next turn will carry. `seen` once a completed turn carried it. |
| `sending`, `running` | Recorded, then in the recipient's work queue until that turn ends. A send interrupted between the two is finished by the delivery loop. |
| `settled` | The result is known and waits for its sender. |
| `returning`, `returned` | Handed over in a turn of the sender, or, for a sender no longer woken, in a notice. |
| `collected` | Read by the sender with `wait`, or refused at once when the message could not be sent. |
| `dropped` | Never handed over. The result stays readable (`wait` with its id, `GET /partners/messages`). |

- The endings of turns are read from Router's settlement feed with a cursor per Agent, so a restart of Mau or of Router loses nothing. Every 15 seconds the open turns are also read from their work events: a turn that ended without an entry in the feed is settled from there, and a turn whose outcome has been unknown for two minutes (Router finds a run again by itself after an interrupted submission) is reported to the sender as `unknown`. Nothing is run again in the partner's place.
- A message whose recipient has not ended its turn after 48 hours fails with `no_answer_after_48_hours`, and that turn is cancelled.
- A hand-over that fails (the turn could not be submitted, or failed) is tried again after 5 s, 15 s, 1 min, 5 min, 15 min, 1 h and 3 h: eight attempts in all, then the result is `dropped`. Waiting for the sending turn to end is not an attempt, and a turn submitted to a busy conversation waits in Router's queue behind the running one. A turn the owner stopped is not repeated.
- A result that could not be handed over for 48 hours is `dropped`, and so is one whose hand-over turn has not ended after 48 hours; that turn is cancelled.
- A sender is woken at most three times in a row for results that all failed. After that a failure leaves a notice in the owner's conversation instead of a turn, until that partner sends a message in a turn the owner started, or a result succeeds.
- A failed or rejected result is final for its message: Mau does not retry the partner's work, run it elsewhere or answer in its place.
- A message in a final state (`returned`, `collected`, `seen`, `dropped`) and a finished hand-over are removed 30 days after they were created; the removal runs once an hour. `wait` with the id of a removed message answers `partner_message_not_found`. What the partners said stays in their conversations.

**What a turn is shown.** A turn in the owner's private conversation, the owner's own and one that hands results over, is given the names and duties of the owner's other partners, and which of them is on the owner's own computer, when its session has not read the same text yet: on the session's first turn and whenever a partner is added, removed or re-paired. A status or a waiting reply changes nothing there: `action=roster` answers those. It stands beside the input (Codex: `additionalContext`; a runtime without it: in front of the input), when its session has the `partners` tool; it and a turn that handles a message are given the `inform` notes left for the partner. At most 30 partners are named there; the roster action lists all of them. The memory reminder is given the same way, to a session that has the `memory` tool. This is not part of the tool definitions or the session's instructions, so it is always current and changes no session fingerprint. How to use the tool is said in places that belong to the tool and to no kernel, each thing once: its description (what holds for every message), the guide a roster returns when asked (recruiting, and how to read what comes back), and the `next` of a `recruit`, `message` or `wait` result that has something of its own to say.

Deleting a partner removes the messages it sent and the finished ones it received. A message another partner still waits on ends as `failed` (`partner_deleted`).

### Partners on another kernel

An environment can offer [more than one kernel](environments.md#more-than-one-kernel-in-an-environment). A partner on a kernel other than Codex is a partner like any other: its own conversation, memory (`memory`, the snapshot in its instructions), the roster and notes beside its input, messages and their results, approvals in the sender's conversation, schedules and model settings from its own runtime. What differs is what the kernel itself offers:

- **Input that no human wrote.** A runtime that takes no native tool output (Agent Host reports `input.nativeItems: unsupported`, as for Claude and Antigravity) is given a partner's message, a hand-over and scheduled work as the text of the same JSON object a Codex partner gets as a tool output: `from`, then `message` or what Mau delivers in its place. Mau records such input as delivered, not as a person's, whichever form it took. This needs Agent Host 0.11.0-alpha.1 or later in the environment: an older Host does not report the capability, and the turn fails with `native_tool_output_unsupported`.
- **What a turn is told.** The roster, the notes and the memory reminder reach such a runtime as a JSON object in front of the input, where Codex has `additionalContext`. Router's routing facts (agent, conversation, source) are not part of it: they stay on the run.
- **Connected apps.** The connector commands in the shell (`gws`, `lark-cli`, `agent-browser`) relay through Codex's command events and work for Codex partners only. Other partners call `connected_apps`, whose catalog carries the connectors' guides ([connector accounts](connector-accounts.md#connector-clis-and-guides-in-the-agents-environment)).
- **Native wake-ups.** Mau's relay of turns that Router did not start (a Codex root woken by its sub-agent) follows Codex runtimes only. A partner on another kernel answers within the turns Router starts.
- **Asking the owner.** A turn that a partner's message started cannot ask the owner, on any kernel. A kernel that asks for permission before running a command needs a non-interactive permission setting in its runtime profile to work in such turns; otherwise the request waits until the Host's deadline and is refused. For Antigravity that setting is the `--dangerously-skip-permissions` argument, not its `auto` mode ([environments](environments.md#an-antigravity-partner)).
- **Native session operations** (history, fork, delete, compaction, steering, skills and native memory management) are what each kernel's adapter in Agent Host supports (Antigravity: resume and history, no compaction, steering, fork or delete); see its [kernel support](https://github.com/Olorinm/agent-kit/blob/main/packages/host/docs/kernel-support.md). The skills and native-memory routes above use Codex's native methods; for a runtime of another kernel the Host refuses them (`native_access_not_enabled`).
- **Background memory review** runs on a restricted Codex runtime, whatever kernel the reviewed partner runs on.
- **Instructions and skills on disk.** Each kernel reads its own files (`AGENTS.md` and `~/.codex/skills` for Codex, `CLAUDE.md` and its own skill directories for Claude, `AGENTS.md`/`GEMINI.md` and its directories under `~/.gemini` for Antigravity). Mau writes none of them for another kernel.

Partners on different kernels share the working directory and nothing of their native context: a session is never moved between kernels, and what one partner knows reaches another as a message.

## Proactive rule contract

Rules contain `agentId`, `targetSessionId` (an existing owner private conversation), `name`, `goal`, `timeZone` (IANA), and `schedule`: either `{type:"interval",minutes:5..10080}` or `{type:"daily",at:"HH:MM"}`. Other fields are assigned `connections`, optional operation names and native skill references, notification mode (`changes`, `always`, `none`), optional quiet hours, `maxRunsPerDay`, `maxToolCalls`, `timeoutSeconds`, and status.

Scheduled work and partner turns use Router's delivery for input that no human wrote: the native standalone tool output for a kernel that takes one (`mau.proactive_work` for a schedule; `mau.partners` for a partner turn in a session that has that tool, Router's `mau.work_sessions` in a session that began before it), and the same JSON object as text for a kernel that does not. It is not a synthetic human instruction, and Mau records it as such whichever form it took. Native tool outputs cannot be combined with `UserInput` skill items: scheduled skill references are validated against native discovery, then supplied by canonical name/path for native on-demand loading. This is not a guarantee of forced skill injection. Explicit user turns can use structured native skill input items through Router.

Daily schedules execute once per local date. A nonexistent DST wall time skips that date; a repeated time uses its first occurrence. Delayed intervals coalesce into one check. A rule has one active trigger, and hitting a budget does not mint replacement triggers. The triggering identity is derived from rule ID, version and scheduled occurrence; manual requests include the caller's stable request ID.

The coordinator lives in Mau's process, with a separate SQLite lease and records. It queues work through Router; Router wakes the configured Environment only for deliverable work. Execution selects a reused per-rule session, a fresh session per occurrence, or an existing conversation. Conversation work can wait for idle execution. Heartbeat is a preset, not another coordinator. A failed or lost submission is reconciled using the same event ID. Unknown execution outcomes remain held and queried, never automatically resubmitted under a new ID.

`execution: {type:"direct",message:"..."}` delivers a fixed reminder through the durable Router outbox without submitting an Agent run. `execution: {type:"agent"}` invokes the native Agent. Neither direct delivery nor a connector precheck needs to wake the Host. Session selection is `{type:"rule"}`, `{type:"fresh"}`, or `{type:"conversation",sessionId:"...",idleOnly:true}`. Notification mode remains independent of execution and session selection.

An explicit `preset:"heartbeat"` supplies a 30-minute interval, the owner conversation from `targetSessionId`, idle-only execution and changes-only notification. Explicit schedule/session/notification fields override that template. A regular task without a preset must provide a schedule.

An optional `precheck: {connectionId,tool,arguments}` calls an assigned read-only connector operation on the trusted server. Its successful result is canonically hashed; equal results skip the Agent, and the first result triggers a run. This only compares the configured query's returned data, not every change in the source. Errors never mean "unchanged". A new checkpoint is committed after successful work, not before execution. Lost precheck outcomes are explicit and do not mint replacement execution identities.

The model returns validated JSON. Each task prompt includes the JSON Schema generated from the same result validator, including string-valued finding versions. In Codex native Code Mode, Mau tool responses are JSON text: scripts must parse a string response before inspecting its `status` or `result`. The task prompt states that boundary explicitly; Mau does not change Codex's native return type. Source IDs must belong to the rule. Cursor proposals require a source-specific trusted connector receipt checked by the `ProactivePort.validateCursor` adapter; the model's JSON alone is never proof. Without that adapter, or if it rejects a proposal, the trigger records `cursorUpdates.status=unverified` and does not advance the cursor. The current product connectors do not supply that receipt adapter, so their cursor advancement is disabled. A verified cursor must also be a decimal monotonic value; opaque cursors are not supported by this initial adapter. Partial failures never advance source cursors. Completion, eligible cursor updates, finding deduplication and notification outbox creation share one transaction.

Notifications use Router's stable outbox identity and receipt query. Quiet hours defer them; user pause holds them. Authorization loss pauses the rule and produces one actionable notice per rule version unless notifications are disabled. Failed and uncertain delivery receipts remain distinct and do not create replacement messages. A `sent` record means Router received the provider's acceptance receipt, not that a person read it. External writes are not exposed by this workflow.

## Trusted grants

Router supplies `HostAdmission` through the embedding interface for owner turns, partner turns and scheduled work. Mau consumes it before public Host HTTP submission. Tool names and model text do not establish authorization. Mau validates owner/partner, current rule state, expiry, call budget and connector operation intersection on every call. The stable tool catalog is retained for the native session and inherited by forks, while each child's calls use its own run grants. Revoked grants stop actual execution immediately. Persisted run requests restore grants after lost start responses and preserve the exact context on retries. Persisted call receipts prevent duplicate execution after worker recreation; ambiguous calls remain uncertain.

## Trusted read tools

Optional `feishuBotReaders` entries in the server configuration select an exact
`agentId` and `owner` with a Feishu bot identity (`appId`, `appSecretFile`, `domain`,
`directory`), or a Cloudflare read broker (`mode: "cloudflare"`, `endpoint`,
`tokenFile`). Mau exposes `feishu_bot_read` through Host's native dynamic tools,
running the official CLI outside the Agent environment. Only CLI-declared reads
whose dry-run plans are read-only may execute. Shell access, identity overrides and
local file paths are not accepted.

The tool is provided only to conversations admitted by Router's channel policy;
unadmitted runs and other Agents receive no grant. The Feishu bot's permissions
still define which records can be read. This is not a per-person authorization
system. Configure channel access accordingly.

The reader reuses existing credentials from private server files. It does not
deploy an OAuth vault or KMS. Personal Feishu authorization and writes require the
separate ConnectorService flow. Model authentication is also separate from this
reader and may still be present in the sandbox.

## Verification

`npm test`, `npm run typecheck`, and the independent package consumer test cover implementation and protocol fixtures. The partner tests run real Router runtimes against a scripted Host: recruiting, the three intents, the reply's way back, restarts, the delivery limits and the approval card in the sender's conversation. The package consumer runs a recruit, a message read with `wait` and a reply returned as a turn through a real Host process. None of this shows how a model uses the tool, or delivery on an external channel. Proactive tests cover lost submission/restart, source isolation, missing and forged cursor proofs, cursor regression, atomic notifications, daily limits, overlap, cancellation during submission, pause, quiet hours, invalid authorization, and DST. These are distinct from real model, cloud wakeup, account access and provider delivery acceptance, which require separate evidence.

No dedicated restricted review runtime is provisioned by default, so background review reports `unsupported / restricted_review_runtime_required` even when its preference is enabled. External notification acceptance and any additional native capabilities require their own evidence.
